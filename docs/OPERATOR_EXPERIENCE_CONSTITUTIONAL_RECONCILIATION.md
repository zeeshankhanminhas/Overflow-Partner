# Overflow Partner — Operator Experience Constitutional Reconciliation

**Status:** Normative acceptance ledger for the existing Operator Experience Recomposition programme  
**Purpose:** Correct incomplete adoption of the already-binding interaction and subtraction constitutions.  
**This is not a new wave.** Where a route failed an original Wave 3–13 exit gate, that original wave remains unfinished until the route conforms.

## Binding acceptance rule

A shared primitive existing in the repository does not satisfy the constitution by itself.

A route is conforming only when its rendered operator experience obeys the existing normative sources:

- `docs/OPERATOR_EXPERIENCE_RECOMPOSITION_SPRINT.md`
- `docs/BUSINESS_LIFECYCLE_CONSTITUTION.md`
- `docs/OPERATOR_SUBTRACTION_CONSTITUTION.md`
- `docs/GLOBAL_STATE_PRESENTATION_CONSTITUTION.md`
- `docs/PRIMARY_NAV_PRODUCT_CONTRACT.md` where applicable

The binding interaction grammar is:

- **Page** — persistent operating context / sustained work
- **Tab / working area** — persistent bounded record aspect
- **Drawer / sheet** — contextual information or work
- **Dialog** — temporary focused business action
- **Disclosure** — rare, advanced, technical, historical or exceptional detail
- **Toast / inline feedback** — action completion feedback only

Non-conforming operator UI is a product defect even when its backend action, React component, typecheck and build are technically correct.

## First-viewport acceptance

Every normal lifecycle record must visibly prioritise:

1. record identity;
2. one authoritative operating state;
3. one next action or waiting condition;
4. no more than 3–4 current decision facts;
5. only unresolved evidence/readiness needed for the current decision.

The first viewport must not contain raw UUIDs/internal IDs, raw enum selectors, selectors for authoritative inherited values, completed-control forms, duplicate current-state presenters or unrelated historical/admin context.

## Lifecycle invariant preserved

The reconciliation must not weaken the hard commercial start gate:

> No positive-value Project execution may start before the required client start payment is actually recorded as received/cleared.

The Project may exist after written client acceptance, but Partner release, access, commencement and execution remain unavailable until qualifying payment. UI simplicity must come from orchestration and interaction depth, not from removing governance.

## Release gate

Wave 14 must not start and the programme must not be declared complete until all of the following are true:

1. original Wave 3–13 route-level adoption gaps are reconciled;
2. lint, typecheck and production build pass on the exact head;
3. the exact Vercel Preview head is READY and runtime-smokeable;
4. the actual rendered application is visually reviewed against the first-viewport and interaction-depth contracts;
5. desktop/mobile and permission variants preserve the same model;
6. Northstar has not been mutated to manufacture a passing result;
7. no lifecycle gate has been bypassed;
8. production/main remain untouched until separately approved.

A future checkpoint must distinguish `implemented in code`, `adopted in rendered route`, `runtime validated`, and `production enforced`. These are not interchangeable states.
